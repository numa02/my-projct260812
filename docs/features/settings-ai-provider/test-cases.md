# テストケース一覧: AIプロバイダ設定

最終更新: 2026-08-16
対象タスク: T-068 / 対応要件: F9
対象画面: `/settings/ai-provider`

## 凡例
- 優先度: P0(必須) / P1(高) / P2(中) / P3(低)
- 種別: 機能 / UI / 性能 / セキュリティ
- 自動テスト: `e2e/settings-ai-provider.spec.ts` でカバーしているものは明記。この画面は外部AIプロバイダを呼び出さず暗号化保存のみのため、E2Eはモックなしで実DBに対して実行している

## 最低限のテスト(P0)

## TC-001: 未設定の状態でフォームが表示され、保存するとAPIキー入力欄がクリアされ「設定済み」になる

- 優先度: P0
- 種別: 機能
- 観点: 正常系
- 自動テスト: `e2e/settings-ai-provider.spec.ts`

### 前提条件
- AIプロバイダ未設定のアカウントでログイン

### 操作手順
1. `/settings/ai-provider` を開く(「APIキー」ラベルの横に「未設定」バッジ、保存ボタンが無効であることを確認)
2. APIキーを入力して保存する

### 期待結果
- 保存前は保存ボタンがAPIキー未入力のため無効
- 保存後「AIプロバイダ設定を保存しました」が表示され、バッジが「設定済み」に変わる
- 「設定済み」は緑のドット付きで表示され、「未設定」との違いが一目で分かる(授業記録画面の「入力済み」と同じ見た目)
- バッジの横に登録済みのプロバイダ名・モデル名(既定のままなら「OpenAI / gpt-5-mini」)が併記される。画面の再読み込みは不要
- APIキー入力欄は保存後クリアされる(平文が残らない)

### 確認した環境
- [ ] Chrome (Mac)

## TC-004: DB上でAPIキーが平文ではなく暗号化されて保存されている

- 優先度: P0
- 種別: セキュリティ
- 観点: 正常系
- 自動テスト: 未対応(開発時にservice_role経由で直接DBを確認し手動検証済み)

1. Supabase Studio等でservice_role権限を使い`ai_provider_setting.encrypted_api_key`カラムを直接確認する

### 期待結果
- 入力した平文のAPIキーがそのまま保存されておらず、base64エンコードされた暗号文になっている

### 確認した環境
- [ ] Chrome (Mac)

## TC-103: 他オリジンからのPUTリクエストがCSRF対策で拒否される

- 優先度: P1
- 種別: セキュリティ
- 観点: 権限
- 自動テスト: 未対応(手動確認、`sec-fetch-site`/`Origin`ヘッダーの偽装が必要)

### 前提条件
- ログイン済みセッションのCookieがある想定で、別オリジンから状態変更リクエストを送る状況を再現する

### 操作手順
1. `sec-fetch-site: cross-site` または異なる`Origin`ヘッダーを付けて `PUT /api/settings/ai-provider` を送信する

### 期待結果
- `FORBIDDEN`(403)が返り、保存されない

### 確認した環境
- [ ] Chrome (Mac)
