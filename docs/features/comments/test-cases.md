# テストケース一覧: 所見管理(クラス単位一覧)

最終更新: 2026-09-11
対象タスク: T-080(T-065〜T-067を再設計・置換)、CM-001〜CM-012(所見管理の再設計。`docs/features/comments/design.md`参照) / 対応要件: F9, F10, F11, F12
対象画面: `/comments/class/[[...id]]`(`id`は任意。生徒名簿画面からの遷移時のみ初期選択クラスのヒントとして付与される)

クラスと対象期間(開始日・終了日、画面全体で1つ)を指定すると、そのクラス全員分の所見入力欄が一覧表示される。氏名と所見入力欄は常時表示、AI生成(F9, F10)は生徒の行ごとに折りたたみで開く。AIで直接生成するかプロンプトを作成するかはAPIキー設定状況から既定値が決まるが、教員はいつでも切り替えられる。

**2026-09の再設計(CM-001〜CM-012)による変更点**: (1) 所見は生徒ごとに常に最新1件のみを保持する方式に変更(過去の所見を期間ごとに複数保持し閲覧する「過去の所見を見る」機能は廃止)。(2) 対象期間(開始日・終了日)はクラスごとにDBへ自動保存され、次回そのクラスを開いたときに復元される(旧仕様はブラウザのローカルstateのみで管理しており、画面遷移のたびに空欄に戻っていた)。このため旧TC-005(対象期間切替で所見が空欄になることを確認するテスト)・旧TC-009(過去の所見を見るセクション)は本ドキュメントから削除し、新仕様に合わせたテストに置き換えている。

## TC-021: フェーズ1マイグレーション適用前から複数期間の所見を持っていた既存ユーザーのデータが正しく扱われる(既存ユーザーデータ)

## TC-022: 段階リリース(2フェーズマイグレーションによる代替)の挙動確認

- 優先度: P0
- 種別: データ整合性
- 観点: 段階リリース
- 自動テスト: 未対応(手動確認。本番相当データでのリハーサルを推奨)

本アプリにはフィーチャーフラグの仕組みがないため、`docs/features/comments/design.md`「段階リリース戦略」に従い、2フェーズマイグレーション自体を段階リリースの代替手段とする。

### 前提条件
- フェーズ1マイグレーション適用直後、まだ新コードがデプロイされていない状態を再現できる

### 操作手順
1. フェーズ1マイグレーション(`class`へのカラム追加・`student_comment`のDEDUP・NOT NULL解除・`unique(student_id)`追加)のみを適用する
2. その状態で、旧コード(period列を参照する所見一覧・履歴閲覧UI)を動かす

### 期待結果
- フェーズ1適用直後でも、`period_start_date`/`period_end_date`列自体はまだ存在するため、旧コードは所見の閲覧・保存とも問題なく動作する(NOT NULLが外れているだけで、旧コードは従来通りこの2列に値を入れて保存するため矛盾しない)
- 新コード(`onConflict: "student_id"`でupsertし、期間列を送らない)をいつデプロイしても、フェーズ1適用後であれば問題なく動作する
- フェーズ2(カラム削除)を適用するまでは、新コードのデプロイに問題が見つかった場合、Vercelのデプロイを前バージョンに戻すだけで旧コードによる運用に復旧できる

### 確認した環境
- [ ] ローカルSupabaseスタックでのリハーサル

## TC-023: マイグレーション前後でデータが一致すること(フェーズ1のDEDUP)

- 優先度: P0
- 種別: データ整合性
- 観点: マイグレーション整合性
- 自動テスト: 未対応(CM-003でローカル手動検証済み。本番適用前にも同様の確認を実施する)

### 前提条件
- ローカルのSupabaseスタックに、複数の生徒・複数期間の所見を含むテストデータを投入済み(1生徒のみ同一`updated_at`の所見を2件含むケースも用意する)

### 操作手順
1. フェーズ1マイグレーション適用前に、生徒ごとの件数・最新の所見の内容を記録しておく
2. フェーズ1マイグレーションを適用する
3. 適用後の`student_comment`を生徒ごとに確認する

### 期待結果
- 生徒ごとに1件のみ残り、残った行の内容が「適用前に記録した、その生徒の最新の所見」と一致する
- `updated_at`が同一の複数行がある生徒では、`id`が大きい方(タイブレーカー)が残る
- `period_start_date`/`period_end_date`のNOT NULL制約が外れている
- 旧複合ユニーク制約(`student_comment_student_id_period_start_date_period_end_dat_key`、63バイトで切り詰められた名前)と新しい`unique(student_id)`制約の両方が存在する

## TC-024: フェーズ1適用後にロールバックしても、データ・機能ともに問題が起きないこと(ロールバック安全性)

- 優先度: P0
- 種別: データ整合性
- 観点: ロールバック
- 自動テスト: 未対応(手動確認、ロールバック演習として実施)

### 前提条件
- フェーズ1マイグレーション適用済み、新コードもデプロイ済み(フェーズ2は未適用)

### 操作手順
1. Vercelのデプロイを、本機能追加前のバージョン(旧コード)にロールバックする(想定演習)
2. 旧コードの所見画面(生徒単位・期間別タブ切替のUI)で、新コードが保存した所見を開く

### 期待結果
- フェーズ2(カラム削除)が未適用であれば、`period_start_date`/`period_end_date`列自体はまだ存在するため、旧コードのSELECT/UPSERTはエラーにならない
- 新コードで保存した所見(`period_start_date`/`period_end_date`が`null`)は、旧コードの「対象期間との完全一致で表示を振り分ける」ロジック上、期間未確定の扱いになり見え方が変わる可能性があるが、データの欠損・破損は起きない
- フェーズ1のDELETEで失われたデータ(不可逆)は、コードロールバックでは復旧できない。復旧が必要な場合はCM-001で検証したバックアップからのリストア手順に従う必要があることをこのテストで再確認する
- **フェーズ2適用後は、このロールバック手順(コードのみを戻す)は成立しない**(`period_start_date`/`period_end_date`列自体が存在しないため、旧コードはエラーになる)。フェーズ2適用のタイミングは、新コードの本番安定稼働を数日確認してからにする(design.md「段階リリース戦略」参照)

### 確認した環境
- [ ] ローカルSupabaseスタックでのリハーサル
