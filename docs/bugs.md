# バグ記録

実装完了後の手動確認・自主レビューで見つかった実バグの記録。原因・修正内容を残すことで、同種のバグの再発を防ぐのが目的(`docs/tasks.md`の各タスクは正常時の実装記録のため、ここでは「壊れていたこと」自体を記録する)。

各エントリの形式:

- **発見経緯**: ユーザー報告 / 自主レビュー(セルフチェック)
- **症状**: 何がどう壊れて見えたか
- **原因**: 根本原因
- **修正**: 対応内容とコミット

## BUG-001: ログイン後のルート(`/`)が未実装のscaffoldのまま表示される

- **発見経緯**: ユーザー報告(スクリーンショット添付。「ログインしてからこちらの画面になるけどどうなっているの？」)
- **症状**: ログイン成功後に遷移するルート(`/`)が、`create-next-app`が生成した初期テンプレートのままだった。ログイン済みユーザーが素のNext.jsロゴ画面を見ることになっていた。
- **原因**: 画面実装(T-049〜T-070)を進める中で、個々の画面(`/classes`, `/students`等)は作られたが、ルート自体(`app/page.tsx`)を差し替えるタスクが計画から漏れていた。`proxy.ts`の`PUBLIC_PATHS`に`/`が含まれていないため未ログイン時は`/login`に飛ぶが、ログイン済みなら`app/page.tsx`がそのまま描画される。
- **修正**: `app/page.tsx`を、クラス管理画面(`/classes`)へリダイレクトする実装に置き換え。全E2Eの`toHaveURL(/\/$/)`アサーションも`/classes`基準に更新。
  コミット: `8244590` ルート("/")を未実装のcreate-next-app初期テンプレートから修正

## BUG-002: クラス未選択状態と表示のズレにより生徒名簿等が空に見える

- **発見経緯**: ユーザー報告(「生徒名簿画面から生徒一覧を見ることも追加することもできないですよ？」)
- **症状**: 生徒名簿画面を開いても生徒一覧・インポート欄が表示されず、常に空白に見えた。クラスの`<select>`自体は何かが選択されているように表示されるが、実際には何も反映されない。
- **原因**: `hooks/useClassOptions.ts`の`selectedClassId`は初期値`null`で、クラスの`<select>`には空文字に対応する選択肢(プレースホルダー)がなかった。そのためReact側の状態は`null`のままでも、ブラウザの`<select>`は見た目上は先頭のクラスを選択済みとして描画してしまい、実際の状態(未選択)と表示がズレていた。生徒一覧の取得・表示は`selectedClassId !== null`をゲートにしていたため、実際には常に未選択(空)として扱われ、何も表示されなかった。
  同じ実装パターン(`<select>`にプレースホルダーがないまま`null`初期値を使う)が`app/(main)/timetable/master/TimetableMasterForm.tsx`の一括モードのクラス選択にも存在することを、本バグの修正中に自主レビューで発見。
- **修正**:
  - `useClassOptions.ts`: 未選択時はクラス一覧の先頭を実際の選択状態として扱う(`effectiveClassId = selectedClassId ?? classes[0]?.id ?? null`)よう変更し、見た目と状態を一致させた。この修正は`students/page.tsx`・`CommentsContent.tsx`・`StudentMemosContent.tsx`すべてに自動的に反映される。
  - `TimetableMasterForm.tsx`: 一括モードのクラス選択も同様に、未選択時は既存データ由来のクラスまたは一覧の先頭を実際の選択状態として扱うよう修正(自主レビューでの発見・修正)。
  コミット: `3c8166a` クラス選択の未選択状態と表示の不一致を修正(生徒名簿等が空に見えるバグ)
- **補足**: 開発中の手動確認(ブラウザ自動操作ツール経由)でも同じ症状に何度か遭遇していたが、当時はブラウザ操作ツール側がReactのchangeイベントを正しく発火していないだけだと誤って判断していた。実際にはアプリ側の実バグだった。

## BUG-003: 所見・生徒別メモ一覧画面の生徒選択にも同種の表示ズレ

- **発見経緯**: 自主レビュー(BUG-002修正後、同じ`<select>`パターンが他にも残っていないか横断的に確認する中で発見。ユーザーからの報告はなし)
- **症状**: 所見画面・生徒別メモ一覧画面で、クラスを切り替えると生徒選択は仕様通りリセットされる(誤って別の生徒を選んだまま操作しないための意図的な設計)が、その際「生徒」の`<select>`に未選択に対応する選択肢がなく、実際には未選択(状態は`null`)にもかかわらずブラウザ上は先頭の生徒が選択済みであるかのように表示されていた。内容ペインは状態(`null`)を見て「生徒を選択してください」を表示し続けるため、見た目と内容の不一致が生じていた。
- **原因**: BUG-002と同じ根本パターン(`<select>`に空選択肢がない状態で`null`初期値を使う)。ただしこちらは「クラス切替時に生徒選択を明示的にリセットする」こと自体は意図された仕様(`docs/design/user-flow.md`補足、および既存E2E「クラスを切り替えると生徒選択がリセットされる」で保証)のため、BUG-002のように先頭を既定選択にする対応は取れない。
- **修正**: 生徒の`<select>`の選択肢の先頭に空文字のプレースホルダー(`{ value: "", label: "選択してください" }`)を追加し、未選択状態を`<select>`の見た目にも正しく反映できるようにした(`CommentsContent.tsx`, `StudentMemosContent.tsx`)。既存E2E(`comments-skeleton.spec.ts`)のオプション一覧アサーションをプレースホルダー込みに更新。
  コミット: `ab5101e` 所見・生徒別メモ一覧画面の生徒選択に未選択プレースホルダーを追加
- **補足(2026-08-17)**: `CommentsContent.tsx`はT-080で所見画面がクラス単位の一覧編集画面(所見管理画面)に再設計された際に削除された。新画面には「生徒」の`<select>`自体が存在しない(クラスの生徒全員を常時一覧表示する構成に変わったため)ため、本バグの対象箇所は`StudentMemosContent.tsx`のみ現存する。

## BUG-004: 教科担任制モードで登録したユーザーが時間割マスタ設定画面を開き直すと一括モードで表示される

- **発見経緯**: ユーザー報告(「教科担任制で登録したユーザーで改めて時間割マスタを開くときに以前のクラス担任制の方で表示されます。登録内容と同じものを表示するようにしてほしいです」)
- **症状**: 教科担任制モード(マスごとに異なるクラスを設定できるモード)で時間割マスタを保存した教員が、後日改めて時間割マスタ設定画面を開くと、常に一括モードが選択された状態で表示される。保存データ自体はマスごとに正しく異なるクラスを保持しているが、画面の初期表示モードが実態と合っていない。
- **原因**: `app/(main)/timetable/master/TimetableMasterForm.tsx`の`mode`状態が`useState<Mode>("bulk")`と常に固定値`"bulk"`で初期化されており、`initialSlots`(サーバーから読み込んだ既存データ)の内容を一切見ていなかった。一括モードで保存した場合と教科担任制モードで保存した場合とでDB上のデータ形状に区別がない(`timetable_master_slot`はどちらのモードで保存してもマス単位の行として保存される)ため、画面を開き直すたびに、実際にどちらのモードで登録されたデータかをpropsから判定する必要があったが、その判定ロジック自体が存在しなかった。
- **修正**: `initialSlots`のうち`classId`が設定されているマスを見て、異なるクラスが2件以上含まれていれば(一括モードでは全マスに同一クラスしか書き込めないため、これは教科担任制モードで保存されたことの確実な証拠になる)、初期表示モードを`"per-class"`とするよう変更した。1件以下の場合は従来通り`"bulk"`のままとする(クラスがまだ1つも設定されていない初回状態や、実際に一括モードで保存されたデータとの互換性を保つため)。
  コミット: `849542f` 教科担任制モードで登録したデータが時間割マスタ設定画面の再訪時に一括モード表示になるバグを修正

## BUG-005: 科目管理画面の「登録」ボタンのE2Eセレクタが2要素に一致し、科目登録を前提とするE2Eが全滅する

- **発見経緯**: 自主レビュー(用語「所感」→「所見」統一(TS-005)のE2E確認中に発見。ユーザーからの報告はなし)
- **症状**: 科目登録を前提処理に含むE2E(`comments-class`・`golden-path`・`memos-record`・`memos-students`・`settings-prompt-template`・`subjects`・`timetable-master`・`timetable-weekly`の8スペック、計26ケース)が、`strict mode violation: getByRole('button', { name: '登録' }) resolved to 2 elements`で失敗する。アプリの挙動自体には問題はない。
- **原因**: コミット`d8d6d5a`(科目の貼り付け一括登録)で科目管理画面に「貼り付けで一括登録」ボタンが追加された。Playwrightの`getByRole`の`name`は既定で部分一致のため、既存の「登録」ボタンのセレクタが新ボタンにも一致するようになったが、E2Eが追従されていなかった。
- **修正**: 8スペックの`getByRole("button", { name: "登録" })`に`exact: true`を付与し、完全一致で指定するよう変更した。
- **補足**: ローカルで`npm run dev`を起動したまま別のworktreeで`npm run test:e2e`を実行すると、`playwright.config.ts`の`reuseExistingServer`により起動中の(別ブランチの)サーバーに対してテストが実行される。worktreeで検証する場合は、元の開発サーバーを止めるか、別ポートで起動したサーバーに向けて実行すること。

## BUG-006: 所見管理画面のE2Eが、対象期間の保存完了を待たずに次の操作へ進み不安定になる

- **発見経緯**: 自主レビュー(生活所見の実装・起算日の廃止で全件E2Eを繰り返すうちに、毎回1〜3件が不規則に失敗することに気づいた。ユーザーからの報告はなし)
- **症状**: `e2e/comments-class.spec.ts`の「クラスを切り替えると、そのクラスに保存された対象期間が復元される」等が、全件実行時のみ不規則に失敗する(単独実行では通る)。アプリの実害はない
- **原因**: 対象期間は入力のたびに`class`テーブルへPATCHで保存され、楽観的更新を行わない方針のため、**保存が成功してキャッシュへ書き込まれて初めて画面の確定値になる**。テスト側は日付を`fill`した直後にクラス切り替えへ進んでいたため、保存完了前に入力欄がアンマウントされると成功時のキャッシュ更新が走らず、後続の復元アサーションが失敗していた(DBへの書き込み自体は行われるため、教員の操作でデータが失われることはない)。加えて、低スペック環境で並列実行すると、サインアップ後の遷移や一覧の描画が既定のタイムアウト(アサーション5秒・テスト30秒)に収まらないことがあった
- **修正**: E2Eの共通ヘルパー`openPeriod`で、対象期間が確定したときだけ消える案内文(「対象期間(開始日・終了日)を指定すると…」)の消失を待つようにし、`comments-class`・`golden-path`・`life-shoken`・`settings-prompt-template`の4スペックで共通化した。あわせて`playwright.config.ts`に`expect.timeout: 10秒`・`timeout: 60秒`・`retries: 1`(CIは2)を設定した(`trace: "on-first-retry"`が設定済みでリトライ前提の記述になっていたため整合させた)。修正後、全件実行を3回連続で失敗0件(うち1回はリトライで1件回復)
- **補足**: PATCHのレスポンスを直接待つ実装も試したが、再読み込み後など既に同じ値が入っている場合はReactのonChangeが発火せず保存自体が走らないため、待ち続けてタイムアウトした。確定状態(画面表示)を待つ方式に変更している

## BUG-007: サイドバーのナビゲーションがフルリロードになり、画面切り替えに体感できるラグがある

- **発見経緯**: ユーザー報告(「クラス管理から生徒管理などの画面を切り替えるときに少しラグがあり気になっています」)
- **症状**: サイドバーのメニューから画面を切り替えるたびに、毎回1〜2秒程度の待ちが発生する。特定の画面に限らず全画面で起きる。
- **原因**: `components/ui/GlobalNav.tsx`のナビゲーション項目が`next/link`の`<Link>`ではなく素の`<a href>`で実装されていた。プロジェクト内の他の箇所(`app/(main)/students/page.tsx`等)では`<Link>`を使っているが、グローバルナビだけが追従していなかった。素の`<a>`はブラウザのフルリロードになるため、クリックのたびに以下がすべてやり直しになる:
  - `proxy.ts`の`supabase.auth.getUser()`が走る。これはCookieを読むだけの`getSession()`と異なり**必ずSupabase Authサーバへネットワーク往復する**ため、HTMLが返る前に1往復分の待ちが入る
  - JSバンドルの再ダウンロード・再パースとReactツリーの再マウント
  - `app/providers.tsx`の`new QueryClient()`が作り直され、**TanStack Queryのキャッシュが全消失**する。そのため直前の画面で取得済みのクラス一覧なども再取得になる
- **修正**: `GlobalNav.tsx`のナビゲーション項目を`next/link`の`<Link>`に置き換え、クライアント遷移にした。これによりフルリロードがなくなり、QueryClientのキャッシュが画面をまたいで保持される。`<Link>`も`<a>`要素を描画するため、`getByRole("link")`で検証している既存の`GlobalNav.test.tsx`・E2Eは変更不要。
- **補足**: 本調査では、ラグを悪化させている要素として以下も確認したが、いずれも本バグとは別件のため本修正のスコープ外としている。
  - `app/providers.tsx`のQueryClientに`defaultOptions`がなく、`hooks/useWeeklyTimetable.ts`以外は`staleTime: 0`(マウントごとに必ず再フェッチ)
  - 同じくQueryClientに`retry`の指定がなく、TanStack Queryの既定(3回・指数バックオフ)が効いている。`CLAUDE.md`の「自動リトライは行わない」方針とずれているため、別途`retry: false`の明示を検討する
  - `app/`配下に`loading.tsx`が1つもなく、遷移中は前の画面が固まって見える
