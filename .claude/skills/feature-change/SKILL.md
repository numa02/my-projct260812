# 機能改修の標準フロー

このプロジェクト(週間時間割・生徒メモ・所感自動生成ツール)で、新機能の追加や既存機能の仕様変更を行うときの標準的な進め方。`CLAUDE.md`のアーキテクチャ方針・命名規則は常に前提として守る。

このフローは`docs/features/comments/`(所感管理の再設計)・`docs/features/subjects/`(科目の標準セット投入)・`docs/features/timetable-master/`(CSV/貼り付け取り込み)の3機能を実装した際の実績から作られている。迷ったときはこれら既存ディレクトリの中身をテンプレートとして参照する。

## 0. 対象かどうかの判断

- **このフローを使う**: 新しい機能を追加する、既存機能の挙動・データモデル・画面構成を変更する
- **使わない(軽量に済ませる)**: 見た目の微調整、タイポ・表記ゆれの修正、明らかな実バグの修正。後者は`docs/bugs.md`に「発見経緯・症状・原因・修正」を記録すれば足りる(`docs/bugs.md`の既存エントリの形式に合わせる)

判断に迷う場合は、ユーザーに一言確認する。

## 1. 要件のヒアリング

依頼内容だけでは実装方針が決まらない場合、コードを書き始める前に確認する。典型的な論点:

- **スコープの境界**: 何が対象で、何が対象外か(既存の`requirements.md`の「スコープ外」節のような明文化を意識する)
- **既存データ・画面の扱い**: 既存データを維持するか、移行が必要か。既存UIを残したまま追加するか、置き換えるか
- **後方互換性**: 旧仕様のデータ・呼び出し元が残っていないか
- **本番反映のタイミング**: 破壊的変更を伴う場合、いつ本番に反映してよいか

不明点がなければヒアリングを省略してよい。ヒアリングを飛ばして実装を始めた後に前提の誤りに気づくより、先に一言確認する方が手戻りが少ない。

## 2. ドキュメント作成

`docs/features/<機能名>/`配下に以下を作成・更新する(既存機能の仕様変更なら、既存のディレクトリがあればそこに追記する)。小さな変更なら`requirements.md`を簡略化してよいが、`tasks.md`は必ず作る(進捗管理・後日の実態確認のため)。

- **`requirements.md`**: 機能概要、ユーザーストーリー、Given/When/Then形式の機能要件、非機能要件、スコープ外、用語、未決事項
- **`design.md`**: データモデルの変更(テーブル・カラム・制約・RPC)、API設計(Hono経由か直接Supabaseか、`CLAUDE.md`のアーキテクチャ原則に従って判断)、画面/UI設計、エラーハンドリング、**影響を受ける既存テスト**(この後のセクション参照)、ロールバック手順
- **`impact.md`**: この変更が既存のどの機能・テスト・ドキュメントに影響するか
- **`tasks.md`**: 機能名の頭文字などから2〜3文字のIDプレフィックス(例: `CM-`, `SJ-`, `TM-`)を決め、`XX-001`から連番でタスクを並べる。各タスクに **DoD(完了の定義)・依存・ロールバック手順** を書く。順序は「データモデル変更 → 既存テスト追従 → フロントエンド基盤(shared・hooks) → UI統合 → モックアップ → E2E → ドキュメント」を基本とする

`docs/features/README.md`にも新しいディレクトリへのリンクを1行追加する。

## 3. アーキテクチャ上の判断(`CLAUDE.md`再掲)

- 単純CRUD → `supabase-js`から直接`insert`/`update`/`delete`/`upsert`
- 複数テーブルにまたがる操作・アトミック性が必要 → Postgres関数(RPC、`SECURITY INVOKER`)を`supabase.rpc()`で呼ぶ
- 秘密情報(APIキー)に触れる処理のみHono経由。新規Honoエンドポイントを安易に追加しない
- 楽観的更新・自動リトライは行わない
- 型は`shared/schemas`のzodスキーマを正とする

## 4. 破壊的DBスキーマ変更は2フェーズ(expand/contract)方式

列削除・NOT NULL追加・ユニーク制約の入れ替えなど、既存コードとの互換性を壊す変更は、**必ず2フェーズに分ける**(`docs/features/comments/design.md`の実績パターン)。理由: マイグレーション適用とVercelデプロイは別パイプラインで原子的に切り替わらないため、1回のマイグレーションで完結させると、適用直後からデプロイ完了までの間、稼働中の旧コードがエラーを返す時間帯が生まれる。

1. **フェーズ1(拡張)**: 新しい列・制約を追加。既存列はそのまま残す(nullable化程度は可)。新コード・旧コードのどちらが動いていてもスキーマ上両立する状態にする
2. 新コードをデプロイし、**本番で数日程度の安定稼働を確認する**(問い合わせ・不具合報告がないこと)
3. **フェーズ2(縮小)**: 旧列・旧制約を削除する。この時点以降はコードロールバックだけでは復旧できない

**フェーズ2適用前に必ず行うこと(このプロジェクトで実際に見落としが発生した箇所)**:

- 削除対象の列を参照している既存のPostgres関数(RPC)がないか、リポジトリ全体を`grep`で確認する。`design.md`に書いた「影響を受ける既存テスト」の一覧だけを信じない。削除対象カラム名でコードベース全体を横断検索し、フロントの型定義だけでなくSQLファイル(RPC定義)・テストのinsertフィクスチャも確認する
- 見つかった参照は、列削除と同じマイグレーションファイル内で`create or replace function`により解消する(関数定義の更新と列削除を同一トランザクションにすることで、中間の不整合状態を作らない)
- ローカルで`npx supabase db reset` → `npm run test:db`(必要なら`npm run test`・`npm run lint`・`npx tsc --noEmit`も)が全て通ることを確認してから本番に進む
- 本番適用前に、削除対象の制約が実際に検出できるか(例: `select conname from pg_constraint where ...`)を本番DBに対して**読み取り専用で**確認する
- 本番の対象テーブルのバックアップ(`pg_dump --data-only`)を取得してから適用する。本番Postgresのバージョンとローカルの`pg_dump`/`psql`のバージョンが食い違うことがあるため(`pg_dump: error: server version ...`)、ローカルのSupabase Docker スタックのコンテナ内蔵`pg_dump`/`psql`(`docker exec <supabase_db_のコンテナ名> pg_dump ...`)を使うと確実

## 5. 実装順序

1. マイグレーション(`supabase/migrations/`) → ローカルで`supabase db reset`
2. 既存のDBレベルテスト(`tests/db/*.test.ts`)をスキーマ変更に追従させる。RPC定義を変更した場合は関連RPCの結合テストも確認する
3. `shared/`の純粋関数(パース処理・バリデーション等)とその単体テスト
4. `hooks/`(TanStack Queryラッパー)
5. UI(`app/`, `components/`)。`docs/design/design-system.md`(トークン)→`design-principles.md`(判断軸)→`components.md`→`screens.md`→`user-flow.md`の優先順で参照する
6. `mockups/<画面>.html`を実装内容に合わせて更新する(**実装だけしてモックを放置しない**。今回このプロジェクトで3画面分のモック更新漏れが発生した)
7. `e2e/`のE2Eテストを追加・更新する
8. `docs/features/<機能名>/test-cases.md`を更新する

## 6. タスク表(`tasks.md`)の運用ルール

**各タスクが完了したら、そのタスクを実装したのと同じコミットでチェックボックスを`[x]`にする。** 「後でまとめてチェックする」を避ける。このプロジェクトでは、機能自体は完成してマージ済みなのにチェックボックスだけ`[ ]`のまま放置され、後日「進捗を確認してほしい」と言われて初めて発覚する、ということが複数の機能で発生した。チェックを入れる際は、完了の根拠(コミットハッシュ等)を短く添えると後から実態確認がしやすい。

## 7. 検証(実装完了とみなす前に)

- `npm run lint`
- `npm run test`(該当する単体テスト)
- DBスキーマ・RPCを変更した場合は`npm run test:db`
- `npx tsc --noEmit`
- 追加・更新したE2E(`npm run test:e2e`。ローカルSupabaseスタックが必要)

## 8. PR作成

1. コード変更前に`EnterWorktree`で作業を分離する(バックグラウンドセッションでは必須。対話セッションでもブランチを切って作業するのが望ましい)
2. 実装・検証が終わったらコミットする
3. リモートにpushし、`gh pr create`でSummary・Test planを含むPRを作成する
4. **`master`への直接push・マージは行わない。** マージはユーザーに依頼する
5. ユーザーにPRのURLと、何を確認してほしいかを伝える

## 9. 本番への反映が必要な場合

- ユーザーの明示的な許可なしに本番へは一切触れない
- 本番DBの接続情報は、チャットに直接貼らずファイル経由で受け取ることを提案する(それでもユーザーがチャットに直接貼ることを選ぶ場合はそれに従う)
- 接続確認 → 事前状態確認(件数・制約の存在確認等、読み取り専用) → バックアップ → 適用 → 適用後の状態確認、の順で進める
- 自動安全装置が本番への書き込み操作(またはPII を含む可能性のある読み取り)をブロックすることがある。その場合は無理に回避しようとせず、正確なコマンドをユーザーに渡して本人の端末で実行してもらい、出力を共有してもらう形に切り替える
